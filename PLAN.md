# canvas++ — plan

A browser extension that improves Canvas LMS. Feature #1 is a **theme engine**: dark is the first theme, with more themes and custom themes later. It's built so other features can plug in after.

## Decisions so far

| Topic                   | Decision                                                                                                         |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Target                  | Canvas LMS: `*.instructure.com` plus schools' custom domains                                                     |
| Audience                | Public: Chrome Web Store + Firefox Add-ons (AMO)                                                                 |
| Browsers                | Chrome (and therefore Edge/Brave/Arc) and Firefox from day one                                                   |
| Stack                   | WXT + TypeScript; Preact via preact/compat (React API) for all UI; theme engine framework-free                   |
| Backend                 | None. All state lives in `storage`; we collect nothing                                                           |
| Default                 | Themes **off** by default; the user turns them on                                                                |
| Trigger                 | Manual toggle (popup, later a keyboard shortcut)                                                                 |
| Engine                  | Our own token-based CSS + a JS contrast pass for course content                                                  |
| Course content          | Readability wins over author colors                                                                              |
| Third-party LTI iframes | Left alone (stay light)                                                                                          |
| Test coverage v1        | Student-facing pages first; teacher pages later                                                                  |
| Positioning             | **Cleaner, more minimal and lighter than Better Canvas.** It has about 2M users but looks cluttered and is heavy |

### What "minimal and light" commits us to

- **Size limits**: content script under 20 KB gzipped, theme CSS under 20 KB gzipped, popup under 20 KB gzipped (Preact included). UI injected into Canvas pages is plain DOM, since it loads on every page view.
- **Runtime:** no work on pages where the extension is off beyond one attribute check. No polling or timers. The MutationObserver only watches content containers.
- **UI:** the popup is one on/off switch per feature (plus, later, a theme picker), grouped into sections by the part of Canvas they change (Appearance, Dashboard, Sidebars & search, Courses). Its main page lists the sections, and each opens to its switches with a back arrow. Themes opens to Ember, Nord, Rosé Pine, Dracula, Everforest, Deep Sea, Tokyo Night, Oxocarbon, Poimandres and a Dark mode page (Dark, Dark (OLED), System). The gear opens the settings: what's set once rather than flipped often (school domains, reset, about). The main page sets the popup's height; every other page keeps to it, scrolls if it's taller, and fades out at an edge with more past it. Every new setting has to justify itself.
- **Themes:** a few carefully designed themes beat many average ones. Leaving Canvas's layout mostly alone and only recoloring it is part of the minimal look.
- Robustness still matters: stable selectors and visual tests, because a minimal extension that breaks every Canvas update isn't clean.

### Open questions

1. Name and branding: "canvas++" is fine for a repo, but check the store listing for trademark issues. Instructure owns "Canvas"; "for Canvas" phrasing is the usual safe pattern.

## Background from research

- **Canvas has no web dark mode.** Only the mobile apps do. On the web there is a per-user High Contrast UI toggle, which is still light.
- **InstUI** (Canvas's React component library) themes through JS/emotion, not CSS variables. Class names look like `css-<hash>-view--block`. The **hash changes between versions; the suffix is stable**, so we target `[class*="-view--block"]` and never the hash.
- Canvas does expose **theme-editor variables** (`--ic-brand-primary`, `--ic-link-color`, `--ic-brand-global-nav-*` …). They only cover brand colors, not surfaces or text, so backgrounds still need selector rules.
- Pages are mostly full page loads with React parts rendered after load (dashboard, planner, discussions, inbox). Inject at `document_start`, then use a MutationObserver for nodes added later.
- **Iframes we can theme:** the Rich Content Editor (TinyMCE, a same-origin `#…_ifr` iframe) and New Quizzes (`*.quiz-lti-*-prod.instructure.com`; always on instructure.com, even for schools on custom domains).
- **Iframes we leave alone:** DocViewer (`canvadocs.instructure.com`), where annotation colors carry meaning; user-uploaded HTML (`*.canvas-user-content.com`); third-party LTI tools.
- Dark Reader's fix list for Canvas is a free map of known problem areas: `.equation_image`, dashboard card badges, InstUI textareas, file download buttons, global nav vars.
- A known failure mode: a dark-mode extension hid quiz questions and answer choices. **Quizzes need dedicated tests.**

## Architecture

```
canvas++/
├─ wxt.config.ts            # manifest generated here (chrome + firefox targets)
├─ src/
│  ├─ entrypoints/
│  │  ├─ background.ts      # service worker: permissions, dynamic script registration
│  │  ├─ canvas.content.ts  # main content script (document_start, all_frames)
│  │  ├─ popup/             # Preact: on/off toggle, theme picker, "enable on this site"
│  │  └─ options/           # Preact: full settings, later the custom theme editor
│  ├─ core/
│  │  ├─ canvas-api.ts      # Canvas REST requests with the user's session (string ids, CSRF)
│  │  ├─ dashboard-cards.ts # keeps a feature's addition on every dashboard card while its setting is on
│  │  ├─ settings.ts        # typed settings schema + storage wrapper + change events
│  │  ├─ features.ts        # feature registry (see below)
│  │  ├─ canvas-detect.ts   # "is this page Canvas?" (window.ENV, #application.ic-app, …)
│  │  └─ domains.ts         # list of enabled custom domains, permission helpers
│  └─ features/
│     └─ themes/
│        ├─ storage.ts      # the setting(s)
│        ├─ page.ts         # turns the theme on/off on the page, no-flash cached copy
│        ├─ palette.ts      # classifies a computed color into a role (pure, unit-tested)
│        ├─ recolor.ts      # tags elements with their roles, once per frame
│        └─ theme.css       # tokens, Canvas variable remaps, one rule per role
└─ tests/
   ├─ fixtures/             # saved Canvas pages (GITIGNORED, has personal data)
   └─ visual/               # Playwright screenshot tests
```

### Feature registry (for later features)

Each feature exports `{ id, name, defaultEnabled, settings schema, apply(ctx), teardown() }`. The content script loads settings once, then runs `apply` for each enabled feature, giving it a context with the document, settings, and an `onSettingsChange` hook. Themes is the first feature. A GPA calculator or a todo tweak would be the next ones, with no changes to the core.

### Theme engine (as built in milestone 4)

Selector files per page turned out to be the wrong tool. Measured on real pages, only 12% of Canvas's color declarations use CSS variables, and InstUI's generated class names don't say which color variant an element uses (the same `-text` class is black, grey, white or link blue). What Canvas does have is a **small, fixed neutral palette**: `#fff` surfaces, `#f2f4f4` secondary surfaces, a ladder of near-black greys for text, light grey borders.

- **Roles, not selectors:** `palette.ts` classifies a computed color by luminance and saturation into a role (`surface` for any light neutral background, `text`, `muted`, `link`, `border`, `border-strong`, `hidden` for white borders). Anything saturated (course colors, status red and green, brand) gets no role and is left alone.
- **Lift:** dark _saturated_ text (course colors as text, status text) gets the `lift` role. CSS keeps its hue and raises its lightness, `oklch(from <color> max(l, 0.75) c h)`, unless it sits on a colored backdrop such as a highlight.
- **Backgrounds by element, not shade:** Canvas is white on white, so containers are invisible; the theme keeps it that way. A light background inside a button or input becomes `control` (lighter), one Canvas lifts with a drop shadow becomes `elevated` (cards, menus, trays; a step lighter), and everything else becomes `page`, the same color as the page. Shadowed callouts in the page flow (InstUI alerts) stay `page`. Flat elements inside a card take the card's color.
- **Decorations made for white:** light "emboss" shadows (`text-shadow`/`box-shadow` such as `1px 1px 0 rgba(255,255,255,.5)`) are removed, because on dark they look like a ghost copy of the text. Light neutral fades (`linear-gradient(..., white)`, also on `::before`/`::after`) are rewritten to fade into the page color. Light SVG strokes (spinner tracks) become the border color.
- **Tagging:** `recolor.ts` sets `data-cpp-bg/-fg/-border` (plus `-emboss`, `-stroke`, `-gradient`) attributes. A MutationObserver queues new elements, and they're tagged in one batch per frame from `requestAnimationFrame`, which runs after the frame's stylesheets have loaded and before it paints. The batch reads every color first, then writes every tag. The first frame is dark, measured as painted. The cost is 2–5 ms per page, about 50 ms once on an 11k-element modules page. It only runs while a theme is on, and tags are inert when it's off.
- **CSS:** `theme.css` holds the token values, remaps Canvas's own variables (link color, font colors, the global nav), styles the page body statically for the first frame, and has one `!important` rule per role.
- **States:** a color Canvas only shows on hover or focus (a grades row turning light blue) doesn't exist when elements are tagged. The first time an element is hovered or focused, `recolor.ts` reads Canvas's color for that state with transitions off, and if it's light, tags the element `data-cpp-state` (`row` gets a faint tint, `control` the lighter control shade). Small components' insides are checked too, since hover styles reach into them (`button:hover > span`).
- **Tokens:** `bg`, `elevated`, `control`, `control-hover`, `hover`, `border`, `border-strong`, `text`, `muted`, `link`, `nav`, `nav-active`, `emphasis` (Canvas's black marks: selected radios, black borders), `lift-l`, `tint-l`, `tint-c`. They grow only when a theme needs another distinction.
- **The global nav takes the theme:** each theme has a `nav` token, its own color apart from page and cards, and remaps Canvas's `--ic-brand-global-nav-*` variables, so the nav is right from the first frame and on any school's colors. The active item is lit from the nav's own color (`nav-active`, whether Canvas drew a link or a button), and counts use the link color. The logo's tile goes while the school's color is dark (`oklch` lightness under 0.6), since that means a light logo that reads on the nav; a light one may mean a dark logo, so the tile stays. Primary buttons keep the school's colors.
- **Themes are data** (milestone 8): a theme is a set of token values, so switching themes rewrites one block of variables. Dark, OLED, Ember (warm brown-black, amber links), Nord (slate blues), Rosé Pine (muted purple), Dracula (grey-violet, pink links), Everforest (grey-green), Deep Sea (dark teal), Tokyo Night (deep indigo, blue links), Oxocarbon (neutral charcoal, pink links) and Poimandres (blue-grey, mint links) are built this way. Nord's, Dracula's and Everforest's surfaces are lighter than the others', so two tokens set how far they lift colored text and tint teachers' highlights, and mid-toned colored text gets its own `lift-mid` role, which only those three act on.
- **No light flash:** see milestone 2. Manifest CSS is injected before the DOM exists, and the attribute is set from a copy cached in the page's `localStorage`.
- **Known limits:** colors a script sets after an element is tagged (a row selected by clicking) are masked by its role, and specific states may need a rule later. Faded "completed" calendar events stay faded, as Canvas intends. The calendar's small month marks days with events and today with a pseudo-element box and the school's button color, which no role reaches, so a theme draws them itself: a ring on the number in the strong border color (Canvas's box is sized to the cell, wider and shorter than the number in its corner) and a circle in the link color.

### Grades on dashboard cards

Off by default (popup switch). On the dashboard (the site root, top frame only), each card gets a pill at the top left of its color/image with the course's current score, linking to `/courses/:id/grades`. Scores come from one `GET /api/v1/courses?enrollment_state=active&include[]=total_scores&include[]=current_grading_period_scores&include[]=restrict_quantitative_data` request, sent the first time grades are on (`features/grades/scores.ts` picks the score, unit-tested). In a course with grading periods it's the current period's score. Courses with nothing to show get no pill: no grades yet, totals hidden, between periods, not a student, or percentages hidden from students (the course's `restrict_quantitative_data`; a letter grade alone doesn't mean that, since every course with a grading scheme has one). The pill uses Canvas's white and text colors, so the theme recolors it like any card element.

### Assignments on dashboard cards

Off by default (popup switch). On the dashboard (site root, top frame), each card ends with a "Due" list of up to 4 items for its course: unfinished work up to 2 weeks overdue (date in red), then everything due in the next 2 weeks, soonest first; finished work stays, struck through and faded. Items come from one `GET /api/v1/planner/items` request (2 weeks either side, `per_page=100`, following `Link: rel="next"`), sent the first time the lists are on. Announcements, calendar events and planner notes are left out. "Done" is Canvas's own planner rule (`core/planner.ts`, unit-tested): the user's planner override wins either way, else a peer review is done once completed and other work once submitted, unless the teacher asked for a redo. Past Canvas's rule, work the teacher graded or excused is done too, since an exam taken on paper is never "submitted". The circle (`core/done-check.ts`) checks an item off in Canvas itself (`POST /api/v1/planner/overrides`, then `PUT …/:id`, with the `_csrf_token` cookie as `X-CSRF-Token`; graded quizzes and discussions through their assignment), so it agrees with Canvas's To Do list and syncs across devices; a refused save is taken back. The planner request and the work it gives are shared with the sidebar's To Do, so checking work off in either shows in both. Better Canvas, by contrast, keeps its checkmarks in extension storage. While a card has a list, its links (Announcements, Assignments, …) sit at the bottom left of its color or image instead of under the title, so the list follows the title and cards get shorter. They're in a pill like the grade pill (white with Canvas's icon grey; the card's shades in the dark theme), since teachers' course images can be busy. This is CSS keyed on `:has(> .cpp-card-due)` (Canvas fixes that area at 146px), so it comes and goes with the list. In the dark theme the pill's colors are `!important`, because the icons may carry roles tagged before the list came. Like the grade pills, the list uses Canvas's own text colors so the theme recolors it, and done rows fade by opacity, which a role can't mask. Lists differ in length, so while they're on, the card container becomes a grid that stretches each card to its row's tallest (rows still size apart, so one long list doesn't stretch the whole dashboard). Its columns keep Canvas's 36px gaps but share the width, cards no narrower than 240px (one full-width column below 620px): the wide nav and To Do sidebar leave less room than Canvas's fixed 262px cards plan for, which dropped to two columns with most of a third's room empty.

### Tidy To Do list (sidebar)

Off by default (popup switch). Canvas's right sidebar (the dashboard's, and a course home's) has a To Do list and Recent Feedback. Canvas's To Do asks the planner for the first 14 unfinished items from two weeks back, and an unread announcement counts as unfinished, so in a recorded dashboard 13 of the 14 were announcements and real work fell off the list. The switch replaces both lists with two of our own in one style: each row a title (two lines at most), its course's code with a dot in the course's color, and on the right its due date or score.

- **To Do:** work only, from the shared planner request (`core/planner.ts`): assignments, quizzes, graded discussions, pages with a to-do date, peer reviews and the user's own notes (no link: they have no page). Announcements and calendar events are left out; unread announcements still show on the dashboard cards' badges, and on a course's page, which has no badge, a line under the list ("2 new announcements") links to the course's announcements while any from the last two weeks are unread. It comes from the same planner response (`plannable.read_state`), so it costs no request, and an announcement the user dismissed or marked done in Canvas's To Do doesn't count. Done and dismissed work is left out. Rows are grouped Overdue (red), Today, Tomorrow, This week, Later (`features/sidebar/todo.ts`, unit-tested), each showing only what its group doesn't say (a time, a weekday, a date). The first 7 show, then "Show N more", which becomes "Show less" once the rest are shown. The heading counts what's left. The circle is the shared one, so work checked off here stays struck through until the page reloads, and its card agrees. If the planner request fails, Canvas's own list stays.
- **Recent Feedback:** read from Canvas's own list, already in the page (`features/sidebar/feedback.ts`), so it costs no request and keeps the teacher's comment, which the grades API doesn't give. Scores are shortened ("95/100"), comments shown in italics up to two lines. The first 3 show (Canvas hides the rest), then "Show N more" (and "Show less" after), and on the dashboard "All grades" replaces Canvas's View Grades button. Canvas doesn't say when feedback came, so it stays in Canvas's order.
- **Course labels:** codes from the user's active courses (`core/courses.ts`, the same request as the card grades, now shared) and colors from `GET /api/v1/users/self/colors`. Without them a row falls back to what Canvas gave. On a course's own pages both lists are that course's, without labels.
- **Page:** `html[data-cpp-sidebar]` hides Canvas's lists, cached in the page's `localStorage` like the logo switch so they don't show for a moment. The dashboard's sidebar comes in a request after the page loads (`/dashboard-sidebar`) and Canvas draws its To Do with React after that, so an observer on `#right-side` adds ours when they come. On the dashboard, To Do's heading line is lowered to continue the Dashboard heading's line. Canvas's hidden To Do still makes its own request.

### Courses in the left sidebar

Off by default (popup switch). Canvas's global nav becomes a 184px sidebar that lists what it otherwise hides behind trays: the user's courses and groups, and the pages they opened last. It takes 100px from the content on every page, in exchange for courses being one click away. 184px is the widest that keeps the dashboard's three cards at a 1440px window. This is a deliberate exception to leaving Canvas's layout alone, which is why it's a switch.

- **Canvas's buttons stay:** they're only moved and restyled with CSS (`features/nav/nav.css`), so their trays and badges keep working. Dashboard, Calendar and Inbox come first, then the lists, then anything else the school added. Account, History, Help and the collapse button are four equal cells along the bottom, so a long list can't push them out of reach. Canvas's white active button is marked like the current course instead, since a row this wide runs straight into a white page; a theme keeps its own mark. Canvas's animations on the nav and its trays are off, since it collapses from one layout to another and everything else here is instant. Switching buttons with a tray open only changes the tray's content, which took keeping a new tray from starting off to the side. Canvas's Courses and Groups buttons are hidden only while our lists exist, so they come back if the lists can't load.
- **Courses:** the dashboard's cards in their order (`GET /api/v1/dashboard/dashboard_cards`, the user's starred courses however they dragged them), labeled by nickname or course code, with the user's colors. Each row shows one count, from the To Do's rules: how much is late, or else how much is due this week. A course that isn't listed, like one from an old term, simply marks no row.
- **Groups:** Canvas's tray's rule (`can_access` and not `concluded`), limited to groups of the listed courses and groups of no course, since courses stay open after their term and the tray fills with old project groups (`core/groups.ts`, unit-tested, shared with the search box along with the request). Each takes its course's color. "Groups" links to all of them.
- **Recent:** the last three pages opened inside a course or group (`GET /api/v1/users/self/history`, what Canvas's History tray shows), once each, without home pages. The one that's open stays, marked like the current course, so a row doesn't vanish when it's clicked. Canvas's history is saved with the list and can lag by more than that, so each such page is also noted as it's opened, named from Canvas's breadcrumbs and kept in `localStorage` per user, and the newest of the two are listed. A new page shows on the next page load. Each has its course's dot, and its name under it in words, since Canvas calls every course's page the same thing ("Course Modules", which loses its "Course") and a color alone has to be matched to the list above. Canvas cuts each batch of 100 visits down after fetching it, so up to four batches are read until there are enough pages. Schools can turn page history off, and then there's no section. Links keep only the path, so they can't leave the site.
- **What's due stays in the right sidebar's To Do.** A "due next" line was tried here, but it was a second To Do list, and one that kept changing at the top of the nav.
- **A course's pages stay in Canvas's course menu.** Listing them in the sidebar was tried: it saved 92px on a course's pages, but one course took more room than all the others and the list moved from page to page.
- **First paint:** the list is saved in the page's `localStorage` with the user's name, since people share computers, and asked for again after 10 minutes. A short-lived observer fills the nav as soon as it's parsed. So counts can be up to 10 minutes behind, as can pages opened on another device.
- **Collapsed:** Canvas's own 54px rail and collapse setting, with each course as a dot and its number. Groups, Recent and the headings' links to all courses and groups aren't on the rail; opening the sidebar brings them back.
- **Left alone:** below 768px (Canvas's mobile header), signed-out pages, and schools on Canvas's new InstUI nav (the `instui_nav` flag, which has no `#global_nav_profile_link`). Trays grow by 100px, as the nav does, since they open underneath it.

### Search (⌘K)

Off by default (popup switch in Sidebars & search, labeled with the platform's shortcut). ⌘K on Apple devices, Ctrl+K elsewhere, opens a search box over any Canvas page (top frame only); the same keys, Escape or a click beside it close it. Ctrl+K stays the browser's on a Mac, where text fields use it, and a contenteditable field keeps the keys, in case it has its own link shortcut (the Rich Content Editor is a frame, so it never sees ours).

- **What it finds** (`features/search/data.ts`, unit-tested): the active courses, named as the sidebar names them (nickname, else code) and found by full name and code too; each current course's menu, as the user sees it (the course's own home tab left out, since the course stands for it), so school-added tools are there; work left to do from the shared planner request; groups (the sidebar's rule); every other assignment in the current courses (quizzes and graded discussions are assignments too), coming up first, then past, then undated, leaving out what the To Do already lists (by assignment id, since a quiz's To Do link and its assignment link differ); every module item in the current courses (pages, files, links…, but not the headings), in module order, found by its module's name too ("week 3 reading"), leaving out the items that are one of the course's assignments, which are listed as themselves (`course-items.ts`, by the content's id: an assignment's, a graded discussion's assignment's, or a quiz's, matched to its assignment's `quiz { _id }`), and linked to its place in the module (`/courses/:id/modules/items/:id`, GraphQL's `url`), as the modules page links them, so an external URL item opens Canvas's page for it rather than the other site; each current course's latest 50 announcements and 50 ungraded discussions (published only; graded ones are assignments), newest first, marked with a megaphone or speech-bubble icon (named, for screen readers and on hover) after the day it was posted, written like a due day ("Thu, Oct 23"), found by their title, by what they say, and by "announcements"/"discussions", leaving out module items that are one of them; assignments (and the To Do's work that's one of them) are found by what their description says, and module pages by their text; then courses whose term is over, and Canvas's own pages (Dashboard, Calendar, Inbox, All grades…). Links only ever go to this site. Before anything is typed it lists the current courses and work due within a week.
- **Recent** (`features/search/recent.ts`, unit-tested): before anything is typed, the last five pages opened that the box lists come first, under "Recent", with the courses and work due under "Courses and work due" (the titles only show when there's something recent). Every Canvas page is noted as it loads, by its path (and the module item it was opened as, from `module_item_id`, since Canvas sends `/courses/:id/modules/items/:id` on to the item's own page), the last 50 in the page's `localStorage` per user (`canvas++:search-visits`, `core/saved.ts`). They're matched to the listed entries by href when the box opens, so pages it doesn't list (a submission, say) are passed over, and the page that's open is left out. A page found by its path wins over its module item, so an assignment opened from a module is listed as the assignment. They're kept apart from the left sidebar's Recent, which only notes pages inside a course or group and only while it's on. Saved with the version like the rest, so an update starts the list over; turning the search off removes it.
- **Matching** (`features/search/match.ts`, unit-tested): every word typed must start a word of the entry, or else appear in it; a word of the title scores above a word of its course, which scores above a part of a word, so "chem gr" finds CHEM 105's Grades and "chem" lists the course before its pages. Ties keep the order above. Case and accents are ignored. What a post, an assignment's description or a module page says is searched too, but a word found only there has to start one of its words (so "lab" doesn't find "available"), and whatever needs the text to match goes after everything else, so common words like "exam" don't push courses and work down.
- **Requests:** none while something is saved for the user until the box opens. With nothing saved (the first page after the switch is turned on, or after someone else's), they're sent once the page has loaded, signed in, so the box opens full the first time. They're one `GET /api/v1/courses?enrollment_state=active&include[]=tabs&include[]=concluded` (the tabs include is undocumented in the allowed list but in Canvas's `course_json`, with the same per-user rules as the tabs API), then two GraphQL requests at once for the current courses (`features/search/course-items.ts`: a `course(id:)` alias per course, the ids as variables). One asks for the assignments and module items: `assignmentsConnection` with `gradingPeriodId: null` so a course with grading periods lists them all, at most 100 a course, each with its `description`; `modulesConnection`, at most 100 modules a course, each with all its `moduleItems`, which Canvas gives in name order, so they're sorted by `position`, a page's with its `_id` and `updatedAt`. The other asks for the posts, `discussionsConnection` twice, filtered by `isAnnouncement`: announcements come newest first, so `first: 50`, and discussions oldest first, so `last: 50`, each with its `message`. They're apart because the posts take longest and a Canvas too old to filter announcements fails only their request. GraphQL has no page bodies, and students usually can't list a course's pages (the pages list was a 404 in all six of the author's courses, whose Pages tabs are hidden), so once the items are in, each module page is asked for on its own (`GET /api/v1/courses/:id/pages/:id`, six at a time, `features/search/texts.ts`), while the posts may still be coming. Each page's text is kept per user with its `updatedAt` (`canvas++:search-pages`), so later refreshes ask only for pages edited since; a locked page's body is a lock explanation, so it's left out. Every text (posts, descriptions, pages) is reduced to its words in a parsed document of its own and cut at 6,000 characters. Announcements were sized from the author's recorded pages: 7 and 30 in two courses ten weeks into the term, typically about 320 characters of text each, the longest 1,670, so 50 is about a term even for a course that posts three a week, and five such courses add under 100 KB to what's saved. On the author's six courses the posts' request was 316 KB together with the items, so it was split: the items took about 0.8 s and the posts about 1.9 s, at once; the 32 module pages (out of 178 files, 59 assignments and 29 links in the modules) came in about 0.7 s, typically 2,500 characters each and 76 KB in all, and the assignment descriptions were mostly empty, though one course had 39 KB of them. Files' text isn't searched: Canvas doesn't give it, and reading PDFs and slides in the page would take megabytes a course and a large library. On the author's six courses (about 300 module items) it was 61 KB uncompressed and about 1 s, against 13 KB and 0.5 s for the assignments alone, plus the groups (`core/groups.ts`), the colors and the planner, each asked for once a page and shared with the other features. The setting keeps a copy in the page's localStorage (`canvas++:quick-search`), so the shortcut works from the first moment of a page load. Past semesters' assignments and module items are left out: they'd crowd every search with old Homework 1s and make the request heavy. The result is kept in the page's localStorage per user (`core/saved.ts`, shared with the sidebar) for 10 minutes, so the box opens full on the next page and is refreshed behind it. It's kept with the extension's version too: what an older version saved counts as nothing, so after an update the first Canvas page asks for it again in the background, and what's new (like module items) is there at once rather than up to 10 minutes later. Reloading an unpacked build doesn't change the version, so while developing, turn the search off and on to start over.
- **In the sidebar** (`features/search/nav-button.ts`): while the search is on, a button that looks like a search field (a magnifier, "Search", the shortcut) is first in Canvas's nav list and opens the box. The search adds it itself, as soon as the list is in the page (`core/nav-menu.ts`, shared with the sidebar), so it's there on the first paint, and `nav.css` shows it only while the sidebar is on; collapsed, it's just the magnifier. The magnifier is a mask on `::before` in the text color, since a theme's recolor pass darkens a light line in an SVG as one drawn for a white page.
- **The box** (`features/search/box.ts`) is in an open shadow root, so Canvas's input styles can't reach it; the theme's `--cpp-*` tokens inherit into it, with Canvas's colors as the fallback. It's a combobox with a listbox (`aria-activedescendant`), the focus stays in its field and goes back where it was on close, and keys typed in it don't reach Canvas's own key handlers, which would otherwise see them as coming from a `<div>`. Results are links, so a middle click opens a new tab; ⌘/Ctrl+Enter does too.

### Time until due

Off by default (popup switch in Courses). After the due dates Canvas shows, in their own text, it says how long is left: "in 40 minutes", "in 5 hours", "tomorrow", "in 3 days", "in 2 weeks" (`features/due/time-left.ts`, unit-tested, in the page's language through `Intl.RelativeTimeFormat`). Under an hour it counts minutes and under a day whole hours, both rounded down so it never claims more time than there is; from a day away it counts calendar days, so "tomorrow" means tomorrow's date. Within a day it's red, like an overdue row on a card. In a row of details ("Due Nov 10 at 11:59pm | in 6 days | -/9 pts") it's an `.ig-details__item` of its own, so Canvas's own separators go around it (" | " on the assignments list, spaces on modules); after the assignment page's date, which has none, it brings a "|" of its own in the date's color. Once the date has passed it hides: Canvas already marks late and missing work, and only it knows whether the work was turned in.

- **Where** (`features/due/page.ts`): an assignment's own page (`time[data-testid="due-date"]` in its header) and a course's assignments list (`.assignment-date-due time`), both from Canvas's date component, whose `<time datetime>` has the exact time; and the modules page, whose `.due_date_display` says only the day ("Dec 4"). Its exact times come from `GET /courses/:id/modules/items/assignment_info`, the request Canvas makes for those days, asked once a page and only when a module item shows a date. The classic assignment page and the classic quiz page write their dates as text only, so they're left alone.
- **Dashboard cards:** with "Assignments on cards" on too, the time left takes the place of each row's day (`.cpp-card-due .cpp-day`, its own element for this), since a card has room for only one; the whole date stays on hover. Overdue work keeps its red day, and done work isn't red however soon it was due.
- **Runtime:** an observer on `#content` labels dates as Canvas draws them. There's no timer: the labels are worked out again when the tab comes back into view, which is when one left open would have gone stale.

### Grade breakdown (Grades sidebar)

Off by default (popup switch in Courses). Canvas's sidebar on a course's Grades page says only "Total: 89.67%" and lists the groups' weights; each group's own grade is at the foot of the table, often a long scroll away. Grade calculators in the Chrome Web Store (group breakdowns, "what do I need") show that's what students go looking for. The switch puts a breakdown at the top of the sidebar: the total large with its letter, how far the next letter is ("0.33% to A-"), how much of the grade it's based on so far in a weighted course ("Based on 60% of the grade so far", while a group like the final exam has nothing graded), and every group with its grade, a bar, its weight and its points ("10% of grade · 29 / 32 pts"; an ungraded group has a dash and an empty bar). There's no "By group" heading, so the groups sit right under the total.

- **Nothing is computed** (`features/grades/breakdown.ts`, unit-tested): the grades are Canvas's, read from the group rows its scripts fill in at the foot of the table (`tr.group_total`) and its total (`.final_grade`), so drop rules, excused work and extra credit are as Canvas has them, and it costs no request. Weights come from Canvas's own table of them, by name, which it renders only in a weighted course. The scheme for the next letter is the `course_active_grading_scheme` Canvas writes into the page's `ENV` script; a letter is found by Canvas's rule (the first cutoff, to four significant digits, the total reaches), and the hint only shows when it agrees with Canvas's letter. Schemes in points get no hint.
- **What's listed:** graded groups, and ungraded ones that will count (a weight above 0). An empty group worth nothing, like Canvas's "Imported Assignments", is left out.
- **What-If:** an observer on the table and the sidebar draws it again whenever Canvas recalculates (a What-If score, the "Calculate based only on graded assignments" checkbox), only when what it shows changed. While Canvas shows its "NOT your official score" note, the total is labeled "Total with What-If" with the actual total under it, kept from before, and a Revert link that clicks Canvas's "Revert to Actual Score".
- **Canvas's controls in a ⋯ menu** (`features/grades/menu.ts`): the "Calculate based only on graded assignments" checkbox, "Show All Details" and "Show Saved "What-If" Scores" were a stack under the sidebar that few use. They sit behind a ⋯ button beside "Total", with a one-line hint ("Click a score in the table to try a What-If grade.") in place of Canvas's four-line paragraph. Each item clicks Canvas's own control, hidden in place, so Canvas's handlers run as before and the items carry Canvas's labels in the page's language. "Show All Details" is a checkbox like the other, checked while Canvas marks its button `showAll`, and keeps that first label while Canvas's turns into "Hide All Details"; both checkboxes keep the menu open. The saved-scores item is there only while Canvas would show its button (`.show_guess_grades.exists`, not hidden). Ticking the checkbox changes no markup, so the menu asks for a render itself. The menu closes on Escape, a pointerdown or focus outside it (not a click: the items' own clicks on Canvas's controls bubble from outside it), and after the saved-scores button.
- **Canvas's sidebar:** all of it under ours is hidden by CSS keyed on `:has(> .cpp-grades)`, so it's back if ours isn't there, with `!important` over the inline display Canvas's scripts show its buttons with. Its "NOT your official score" note is hidden only while ours has a total to put its Revert by. Colors are Canvas's text greys and link color, or the theme's tokens (`--cpp-muted`, `--cpp-border`, `--cpp-elevated` for the menu); the bar's track is the text color at 12%, which reads on any background and gets no role.
- **Left alone:** courses that hide percentages from students (Canvas draws a different page, with no `#grades_summary`), and the rest of the page. A course with weighted grading periods lists its periods, read the same way; no recorded course has them.

### Hiding the school logo

Off by default (popup switch). It hides the school's logo at the top of the global nav with `display: none` on `.ic-app-header__logomark-container`, so the nav's buttons move up into the logo's space, in the expanded and the collapsed nav alike. It also takes the logo's link out of the tab order and away from screen readers; the Dashboard button goes to the same place. The switch is `html[data-cpp-hide-logo]`, cached in the page's `localStorage` like the theme (`core/page-mirror.ts`) so the logo doesn't show for a moment on every page load. The theme's recolor pass only takes off the tags it sets, so switches like this one survive it.

### Hiding the footer

Off by default (popup switch). It hides the bar of Instructure's links at the bottom of every page (Privacy Policy, Cookie Notice, Acceptable Use Policy, Facebook, X.com) with `display: none` on `#footer.ic-app-footer`; nothing comes after it, so nothing else moves. The switch is `html[data-cpp-hide-footer]`, cached like the logo's: both go through `core/page-flag.ts`, which tags `<html>` while a switch is on and keeps the copy in the page's `localStorage`.

### Hiding SensusAccess

Off by default (popup switch), since some students rely on the tool. SensusAccess Inside is a third-party tool a school can add to Canvas: its "S" buttons convert a file or page to audio, Braille, an e-book and so on. Canvas doesn't list it as a tool: the school's global JS loads it, and its script adds the buttons to list rows (modules, files, assignments, quizzes, discussions, announcements) and the headings of content pages, each wrapped in `.sensus-access-button-item`, which takes `display: none` under `html[data-cpp-hide-sensus]` (`core/page-flag.ts`, like the footer). On the Pages list the wrapper is a `td` and the script also appends an empty `th` to `tr.header-row`; that's hidden too, only while the list has the buttons, since Canvas's own last header cell can be empty. Its enable/disable link in Course Settings (`.sensus-enable-disable`) goes with them. No recorded page has the Pages list or Course Settings, so the e2e tests use the script's markup; the Pages list was also checked once on live Canvas, while Course Settings answers 401 for students. The scripts still load: this only hides what they add.

### Contrast pass (course content, as built in milestone 6)

Teachers write course content in Canvas's editor, which offers 22 colors (TinyMCE's default map) for text and highlight. Canvas renders it inside `.user_content` on every content page (pages, assignments, announcements, discussions, both quiz types, the syllabus). Measured with the theme on, colored _text_ already read through `lift`; colored _backgrounds_ didn't: the theme made the text light but left a highlight, colored table cell or callout box as written, so light highlights fell to about 1:1.

- **Tint:** inside `.user_content`, a background too light for the theme's text (luminance above 0.12; `tints()` in `palette.ts`) is tagged `tint`, and CSS turns it into a dark shade of its own hue (`oklch(from <color> var(--cpp-tint-l) min(c, var(--cpp-tint-c)) h)`, 0.32 and 0.07 in the dark theme). Yellow stays recognizably yellow, and light text reads on it at 8:1 or better. Light neutral ones are surfaces as before; dark ones (a teacher's navy banner with white text) read as they are and stay.
- **Text on a tint:** dark colored text on a tinted background is lifted like colored text on the page (`liftsOn(…, content)`). Outside course content, colored backgrounds (Canvas's badges, course colors) still keep dark text and their colors.
- **Restore on disable:** nothing to do. Like every tag, `tint` is inert without `html[data-cpp-theme]`, which the test checks by turning the theme off again.
- **Test:** `tests/e2e/course-content.spec.ts` renders every editor color as text and highlight, plus common combinations, tables and callouts, and requires each to read at 4.5:1 with the theme on, or no worse than the teacher made it. The recorded courses use no inline colors, so the visual tests can't catch this.
- **Known limits:** the Rich Content Editor's frame is never tagged (see milestone 5), so a highlight is still light text on a light color while editing. A pale color close to grey (`#d1ecf1`) counts as a neutral surface and goes flat, losing its box but staying readable. `.equation_image` (black ink on transparent) is untested: none of the recorded pages have one.

### Domains and permissions (as built in milestone 7)

- **Manifest:** `permissions: ["storage", "scripting", "activeTab"]`, `optional_host_permissions: ["https://*/*"]`. The content script's own match (`https://*.instructure.com/*`) is the only host access at install, so the install prompt has no "all websites" warning. Firefox needs 128+ (optional host permissions, `matchOriginAsFallback` in registrations).
- **Custom domain flow:** on a site that isn't instructure.com, opening the popup (`activeTab`) lets it check the page for Canvas's app shell or brand stylesheet (`features/domains/detect.ts`). If it's Canvas, the popup offers to **Enable** canvas++ there, which calls `permissions.request` for that site as the first thing in the click (Firefox requires it, and may close the popup for the prompt).
- **The grants are the list:** the background keeps one runtime-registered content script (the same built files as the manifest one) matching exactly the granted custom domains, and themes tabs already open on a newly granted one. No domain list is stored. The popup's settings list the grants and remove them.
- **Upkeep:** both browsers drop runtime registrations when the extension updates (checked in Chromium's and Firefox's source), so the background re-syncs on `runtime.onInstalled`, `permissions.onAdded` and `permissions.onRemoved`. Grants made from the browser's own site-access menu are picked up the same way.

### Settings

`storage.sync` limits: 100 KB total, 8 KB per item, 120 writes per minute. Store small settings there: enabled, theme id, per-feature settings, custom themes (one key each). Store the domain list and caches in `storage.local`. The content script listens to `storage.onChanged`, so toggling never needs a reload.

### Firefox notes (verify while building)

- WXT handles `browser.*` vs `chrome.*` and builds both manifests.
- Firefox MV3 treats host permissions as user-grantable. Check that `*.instructure.com` is actually granted on install and that the popup handles it when it isn't.
- Check `match_origin_as_fallback` and `registerContentScripts` support in current Firefox versions.

## Testing

- **Fixtures (built in milestone 3):** `npm run fixtures:record` signs in to your Canvas, discovers about 20 student pages and saves each as a HAR (every request and response, so the page replays offline with Canvas's own JS). Login cookies are stripped and a custom domain is rewritten to `fixture.instructure.com` so the content script runs on it. **They contain your name, grades and classmates' names, so they stay gitignored.** If we ever commit fixtures, scrub them first. agent-browser was tried for recording but loses the bodies of preloaded assets (Canvas's main bundle and fonts), so Playwright records.
- **Playwright with the extension loaded** (persistent context + `--load-extension`, in Chrome for Testing, which still allows that and never auto-updates):
  1. **Visual tests:** replay each fixture with a frozen clock, theme off and on, and compare full-page screenshots against approved baselines with a tight color threshold. This is how we "don't break". The off screenshots also prove our CSS does nothing while off.
  2. **Contrast audit:** axe-core's color-contrast rule on each fixture. The theme may not add violations Canvas doesn't already have.
  3. **Live smoke test:** run against the real Canvas with a saved logged-in profile. Run it manually, not in CI.
- **Unit tests (Vitest):** contrast math, settings schema migrations, `canvas-detect`.
- **Quizzes get their own checklist:** classic quiz and New Quizzes. Every question type renders, answer choices are visible, and selected/correct states are distinguishable.
- **Teacher pages:** later. Free-for-Teacher signups appear limited in 2026, so check canvaslms.com/try-canvas. The fallback is running open-source canvas-lms locally in Docker.

## Risks

| Risk                              | Mitigation                                                                                      |
| --------------------------------- | ----------------------------------------------------------------------------------------------- |
| Canvas UI updates break rules     | Stable selectors only, visual tests, and a scheduled live smoke run                             |
| Quiz content hidden or unreadable | Dedicated quiz fixtures + checklist. Never set `color` equal to the background on inputs/labels |
| Contrast pass slows huge pages    | Process only added subtrees, debounce, skip containers that aren't content                      |
| Light flash on load               | Manifest CSS + localStorage copy read synchronously at `document_start`                         |
| Store rejection over permissions  | Narrow required hosts, optional per-domain hosts, clear justifications                          |
| Copying Better Canvas             | Use it only as a reference for _which_ areas need styling. Write our own rules                  |
